# 目的
当たり前のように使っている「インデックス」を改めて言語化して説明してみようという思いつき

# インデックスとは

## 一言で言うなら
よく言われるのは「辞書の索引」

インデックスがなければ、知りたい用語を探すために１ページ目から最後のページまで全部めくらなきゃいけない  
インデックスがあれば、知りたい用語が何ページ目にあるかをパッと特定してそのページだけ直接開くことができる

## 貼りまくればいい？
そういうわけでもない  
検索が早くなる代わりに、追加・更新・削除が遅くなるというトレードオフが発生する  

本の中身（データ）が変わるたびに索引（インデックス）を毎回書き直す必要がある  
加えて、索引自体の場所（容量）が必要になる

## 実際どれくらい速くなるの？
環境にもよると思うが、どれくらいの検索速度の差があって、どのくらいデータを追加・更新に影響するか  
せっかくなので調べてみよ〜という感じ

### 検証環境を準備する
環境差を少しでも抑えるため、Dockerコンテナに CPU とメモリの上限を設定する（今回は2vCPU/4GiBメモリ環境）

```bash
docker run --rm --name lab-mysql \
  --cpus=2 \
  --memory=4g \
  --memory-swap=4g \
  -e MYSQL_ROOT_PASSWORD=password \
  -p 127.0.0.1:3306:3306 \
  -d mysql:8.4
```

### 検証データとして1000万行のデータを作る

まず検証用のデータベースと、1〜10000000 の連番を作る一時テーブルをSQLクエリで用意する  
`category_id` は1〜1000を繰り返すので、各カテゴリは約10000行ずつになる


| カラム名 | データ型 | 内容 |
| --- | --- | --- |
| `id` | `BIGINT` | 1から10000000までの連番 |
| `category_id` | `INTEGER` | 1から1000までを繰り返すカテゴリID |
| `created_at` | `TIMESTAMP` | 連番を秒数として加算した日時 |
| `payload` | `TEXT` | 100文字のダミーデータ |

```sql
CREATE DATABASE index_lab;
USE index_lab;

CREATE TEMPORARY TABLE seq AS
SELECT
  d0.n + d1.n * 10 + d2.n * 100 + d3.n * 1000 + d4.n * 10000 + d5.n * 100000 + d6.n * 1000000 + 1 AS n
FROM
  (SELECT 0 AS n UNION ALL SELECT 1 UNION ALL SELECT 2 UNION ALL SELECT 3 UNION ALL SELECT 4
   UNION ALL SELECT 5 UNION ALL SELECT 6 UNION ALL SELECT 7 UNION ALL SELECT 8 UNION ALL SELECT 9) AS d0
CROSS JOIN
  (SELECT 0 AS n UNION ALL SELECT 1 UNION ALL SELECT 2 UNION ALL SELECT 3 UNION ALL SELECT 4
   UNION ALL SELECT 5 UNION ALL SELECT 6 UNION ALL SELECT 7 UNION ALL SELECT 8 UNION ALL SELECT 9) AS d1
CROSS JOIN
  (SELECT 0 AS n UNION ALL SELECT 1 UNION ALL SELECT 2 UNION ALL SELECT 3 UNION ALL SELECT 4
   UNION ALL SELECT 5 UNION ALL SELECT 6 UNION ALL SELECT 7 UNION ALL SELECT 8 UNION ALL SELECT 9) AS d2
CROSS JOIN
  (SELECT 0 AS n UNION ALL SELECT 1 UNION ALL SELECT 2 UNION ALL SELECT 3 UNION ALL SELECT 4
   UNION ALL SELECT 5 UNION ALL SELECT 6 UNION ALL SELECT 7 UNION ALL SELECT 8 UNION ALL SELECT 9) AS d3
CROSS JOIN
  (SELECT 0 AS n UNION ALL SELECT 1 UNION ALL SELECT 2 UNION ALL SELECT 3 UNION ALL SELECT 4
   UNION ALL SELECT 5 UNION ALL SELECT 6 UNION ALL SELECT 7 UNION ALL SELECT 8 UNION ALL SELECT 9) AS d4
CROSS JOIN
  (SELECT 0 AS n UNION ALL SELECT 1 UNION ALL SELECT 2 UNION ALL SELECT 3 UNION ALL SELECT 4
   UNION ALL SELECT 5 UNION ALL SELECT 6 UNION ALL SELECT 7 UNION ALL SELECT 8 UNION ALL SELECT 9) AS d5
CROSS JOIN
  (SELECT 0 AS n UNION ALL SELECT 1 UNION ALL SELECT 2 UNION ALL SELECT 3 UNION ALL SELECT 4
   UNION ALL SELECT 5 UNION ALL SELECT 6 UNION ALL SELECT 7 UNION ALL SELECT 8 UNION ALL SELECT 9) AS d6;

CREATE TABLE records (
  id          bigint NOT NULL,
  category_id integer NOT NULL,
  created_at  timestamp NOT NULL,
  payload     text NOT NULL
) ENGINE=InnoDB;

INSERT INTO records (id, category_id, created_at, payload)
SELECT
  seq.n,
  MOD(seq.n, 1000) + 1,
  TIMESTAMP('2020-01-01 00:00:00') + INTERVAL seq.n SECOND,
  REPEAT('x', 100)
FROM seq;

CREATE TABLE records_with_index LIKE records;
INSERT INTO records_with_index
SELECT * FROM records;

CREATE INDEX records_category_id_idx ON records_with_index (category_id);
```

> `records` はインデックスなし、`records_with_index` は `category_id` のインデックスありの比較用テーブル
{: .prompt-tip }

### 読み取り性能を比べる


```sql
-- インデックスなし
mysql> EXPLAIN ANALYZE SELECT * FROM records WHERE category_id = 42;
+---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
| EXPLAIN                                                                                                                                                                                                             |
+---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
| -> Filter: (records.category_id = 42)  (cost=1.06e+6 rows=965960) (actual time=5.84..4852 rows=10000 loops=1)
    -> Table scan on records  (cost=1.06e+6 rows=9.66e+6) (actual time=3.8..4533 rows=10e+6 loops=1) |
+---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
1 row in set (4.86 sec)

-- インデックスあり
mysql> EXPLAIN ANALYZE SELECT * FROM records_with_index WHERE category_id = 42;

+------------------------------------------------------------------------------------------------------------------------------------------------------------+
| EXPLAIN                                                                                                                                                    |
+------------------------------------------------------------------------------------------------------------------------------------------------------------+
| -> Index lookup on records_with_index using records_category_id_idx (category_id=42)  (cost=11000 rows=10000) (actual time=1.04..2496 rows=10000 loops=1)  |
+------------------------------------------------------------------------------------------------------------------------------------------------------------+
1 row in set (2.51 sec)

```



> `Index lookup on ...` はインデックスを使っている証拠
{: .prompt-tip }

`actual time`は例えば「`actual time=5.84..4852`」なら `5.84`が最初の行が返るまで約5.84msかかって、`4852`が残りの行も処理し終わるまで約4852msかかったということを示している


今回で言うとこんな感じ

| 条件 | 最初の1行が返るまで | 全行（検索結果の1万行）が返るまで |
| --- | ---: | ---: |
| インデックスなし | 約0.006秒（5.84ms） | 約4.852秒（4852ms） |
| インデックスあり | 約0.001秒（1.04ms） | 約2.496秒（2496ms） |



### インデックスが使う容量を比べる

```sql
mysql> SELECT
    ->   table_name,
    ->   ROUND(data_length / 1024 / 1024, 2) AS data_size_mb,
    ->   ROUND(index_length / 1024 / 1024, 2) AS index_size_mb
    -> FROM information_schema.tables
    -> WHERE table_schema = DATABASE()
    ->   AND table_name IN ('records', 'records_with_index');
+--------------------+--------------+---------------+
| TABLE_NAME         | data_size_mb | index_size_mb |
+--------------------+--------------+---------------+
| records            |      1462.00 |          0.00 |
| records_with_index |      1462.00 |        170.70 |
+--------------------+--------------+---------------+
2 rows in set (0.00 sec)
```

今回の出力を表にするとこんな感じ

| テーブル | データ容量 | インデックス容量 |
| --- | ---: | ---: |
| `records`（インデックスなし） | 1462.00 MB | 0.00 MB |
| `records_with_index`（インデックスあり） | 1462.00 MB | 170.70 MB |

> `records_with_index` の`index_size_mb`が0.00の場合は`ANALYZE TABLE records, records_with_index;` を実施する
{: .prompt-tip }

### 書き込み性能を比べる

それぞれに追加で同じ1000万行を挿入し、開始・終了時刻の差を比べる  
これにより、すでに1000万行あるテーブルへの追加書き込みを比較できる

MySQL の `EXPLAIN ANALYZE` は SELECT 用なので、INSERT の計測には使わない

```sql
mysql> SET @started_at = NOW(6);
Query OK, 0 rows affected (0.00 sec)

mysql> INSERT INTO records (id, category_id, created_at, payload)
    -> SELECT
    ->   seq.n + 10000000,
    ->   MOD(seq.n, 1000) + 1,
    ->   TIMESTAMP('2020-01-01 00:00:00') + INTERVAL (seq.n + 10000000) SECOND,
    ->   REPEAT('x', 100)
    -> FROM seq;

Query OK, 10000000 rows affected (51.32 sec)
Records: 10000000  Duplicates: 0  Warnings: 0

mysql> SELECT TIMESTAMPDIFF(MICROSECOND, @started_at, NOW(6)) / 1000000 AS elapsed_seconds;
+-----------------+
| elapsed_seconds |
+-----------------+
|         51.3245 |
+-----------------+
1 row in set (0.00 sec)

mysql> SET @started_at = NOW(6);
Query OK, 0 rows affected (0.00 sec)

mysql> INSERT INTO records_with_index (id, category_id, created_at, payload)
    -> SELECT
    ->   seq.n + 10000000,
    ->   MOD(seq.n, 1000) + 1,
    ->   TIMESTAMP('2020-01-01 00:00:00') + INTERVAL (seq.n + 10000000) SECOND,
    ->   REPEAT('x', 100)
    -> FROM seq;
Query OK, 10000000 rows affected (1 min 31.11 sec)
Records: 10000000  Duplicates: 0  Warnings: 0

mysql> SELECT TIMESTAMPDIFF(MICROSECOND, @started_at, NOW(6)) / 1000000 AS elapsed_seconds;
+-----------------+
| elapsed_seconds |
+-----------------+
|         98.4528 |
+-----------------+
1 row in set (0.00 sec)
```

今回で言うとこんな感じ

| 条件 | 1000万行のINSERTにかかった時間 |
| --- | ---: |
| インデックスなし | 約51.32秒 |
| インデックスあり | 約98.45秒 |

今回の計測では、インデックスありの方が約47.13秒長く、約1.92倍の時間がかかった

### まとめ

今回の計測では、`category_id` のインデックスを使うことで検索時間が短くなった一方、追加のINSERTにはより時間がかかり、インデックス分の容量も必要になった  
検索性能の向上と、書き込み性能・ストレージ容量とのトレードオフを確認できた

ただし、ここでの時間や容量は今回のデータ量・検索条件・実行環境での結果であり、行数や環境が変わっても同じ倍率になるとは限らない  
どのインデックスを作るかは、実際の検索頻度や書き込み頻度、許容できる容量を考えて判断する必要がある
